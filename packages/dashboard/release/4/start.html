Protect your site

After these five steps, no single key can change what your website asks wallets to sign: your CI only proposes each release, your approvers approve it in their own wallets, and TapeOut circuit #6 decides when it may go live. Users who run Guard are checked against exactly what you sealed.

You need: Node.js 18+, a static site built by GitHub Actions (output folder such as dist/), a wallet on X Layer with ~0.001 OKB, and three approver addresses.

Fastest: one command

In your project folder. It asks for your domain, the gate address (it tells you how to create it in the dashboard), your host and your build command, then writes the proposer key, signet.config.json, the domain proof, your host's header file and .github/workflows/signet.yml. It sends no transaction.

npx -y signetguard@0.1.3 init

Same thing without questions (CI, scripts): signet init --domain app.example.org --gate 0x… --host cloudflare --yes. Hosts: cloudflare, netlify, vercel, github-pages, other. Or follow the five steps below by hand.

1 · Install the CLI

In your project folder:

npm install -g signetguard
signet --version
signet keygen

The signetguard package: one file, no dependencies, Node 18+. The same package is also served here: npm install -g https://signetguard.xyz/signetguard-0.1.3.tgz.

signet keygen creates your CI proposer key in .signet/proposer.key (git-ignored) and prints only its address. Keep the address for step 2. The key can propose and publish releases; it can never approve one.

2 · Create your gate

Open Protect a site in the dashboard, connect your wallet (it offers to switch to X Layer), and enter your domain, three approver addresses, the CI proposer address from step 1, a recovery address kept offline and, optionally, a guardian that can only freeze. Two transactions: 1. Reserve the domain, then, two blocks later, 2. Create the gate (≈ 0.000013 OKB of gas). The page then shows your gate address.

3 · Prove you control the domain

In your project folder, with your domain and the gate address from step 2:

signet link app.example.org 0xYourGateAddress
signet domain public

signet link writes signet.config.json (commit it). signet domain public writes public/.well-known/signet.json naming your gate; use the folder your build copies to the site root. Serve it with Access-Control-Allow-Origin: * so the dashboard and badge can read it (Cloudflare Pages and Netlify: add to public/_headers):

/.well-known/signet.json
  Access-Control-Allow-Origin: *

(Vercel: the same header in vercel.json.) Deploy your site once with the file, then check:

signet domain --check

Behind Cloudflare? Turn off Email Obfuscation and Rocket Loader for your site, and anything else that rewrites HTML or scripts on the way out. They change the bytes your visitors get after you sealed them, so Guard shows the site as not matching its release. (Email Obfuscation rewrites any text that looks like an email address, even name@1.2.3, and adds a script.) Check the live bytes against your build with signet verify https://your-domain --build dist.

Only someone who controls the domain can publish this file. Guard, the dashboard, the badge and the watchtower ignore a gate until its domain serves this file naming it, so nobody can seal a domain they don't control.

4 · Add the GitHub workflow

  1. Repository → Settings → Secrets and variables → Actions → New secret SIGNET_PROPOSER_KEY = the content of .signet/proposer.key. Then delete the file from your machine.
  2. Send the CI proposer address ≈ 0.0005 OKB on X Layer for gas (propose + publish + the release's manifest files).
  3. Add .github/workflows/signet.yml, with your own build and deploy commands:
name: Signet release
on:
  push:
    branches: [main]
jobs:
  release:
    runs-on: ubuntu-latest
    timeout-minutes: 360
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 20
      - run: npm ci && npm run build            # your build; output in dist/
      - run: npm install -g signetguard@0.1.3
      - name: Seal and propose (the CI key can only propose)
        run: signet verify dist && signet seal dist && signet propose dist --reuse
        env:
          SIGNET_PROPOSER_KEY: ${{ secrets.SIGNET_PROPOSER_KEY }}
      - name: Wait for the approvals and the timelock, publish (the circuit decides), store the manifest Guard reads
        run: signet wait dist --publish --timeout 19800
        env:
          SIGNET_PROPOSER_KEY: ${{ secrets.SIGNET_PROPOSER_KEY }}
      - name: Deploy (only reached after the release is published)
        run: echo "your deploy command here"

signet wait --publish also writes the release's 3 manifest files on-chain (allowlist, origins, file list; ≈ 0.00003 OKB), which is what Guard checks your site against. A re-run skips files that are already stored.

Deploy only after signet wait succeeds: that is what makes an unapproved build unable to go live. A first release is tier 10 (2 approvals + 24 h), longer than a 6-hour GitHub job: when the job times out, re-run it after the 24 h; propose --reuse finds the same proposal.

Your host

Whatever the host, the rule is the same: deploy the exact folder you sealed, after signet wait succeeds, with no build or rewriting on the host's side. signet init writes all of this for you.

Cloudflare Pages

Header for the proof, in public/_headers:

/.well-known/signet.json
  Access-Control-Allow-Origin: *

Deploy step (secrets CLOUDFLARE_API_TOKEN, CLOUDFLARE_ACCOUNT_ID):

npx -y wrangler@4 pages deploy dist --project-name YOUR_PROJECT --branch main

Turn off Email Obfuscation and Rocket Loader for the site (Cloudflare dashboard), and anything else that rewrites HTML or scripts. They change the bytes after you sealed them, so Guard and the watchtower see a mismatch.

Netlify

Header for the proof, in public/_headers (same format as Cloudflare). Deploy step (secrets NETLIFY_AUTH_TOKEN, NETLIFY_SITE_ID):

npx -y netlify-cli@17 deploy --dir=dist --prod --no-build

Turn off Netlify's asset optimization / post processing if it's on: it rewrites files after the seal.

Vercel

Header for the proof, in public/vercel.json (deployed as a static folder, so the file goes inside it):

{"headers":[{"source":"/.well-known/signet.json","headers":[{"key":"Access-Control-Allow-Origin","value":"*"}]}]}

Deploy step (secrets VERCEL_TOKEN, VERCEL_ORG_ID, VERCEL_PROJECT_ID). Deploy the sealed folder, not the source, so Vercel doesn't rebuild it:

npx -y vercel@39 deploy dist --prod --yes --token "$VERCEL_TOKEN"
GitHub Pages

Pages already allows cross-origin reads. Add an empty public/.nojekyll so the .well-known folder is served. Settings → Pages → Source: GitHub Actions, then deploy the sealed folder:

      - uses: actions/upload-pages-artifact@v3
        with:
          path: dist
      - uses: actions/deploy-pages@v4

The job needs permissions: pages: write, id-token: write and environment: github-pages.

5 · Approve your first release, add the badge

Push to main. The workflow proposes release #1. Two approvers open the dashboard, open your domain, read Diff Guard, and click Approve in their own wallets. After the timelock the workflow publishes and deploys.

Then open https://signetguard.xyz/app#/badge/<your domain> and copy the "Sealed by Signet" badge into your site footer. It links to a live page that reads the chain.

Your gate starts in observe mode (Guard reports, never blocks). Switch to enforce in the dashboard when your releases flow cleanly.

Questions

Do my contracts change?
No. Signet seals your website's files and the list of contracts it may call; your contracts stay as they are.
What does it cost?
Gas on X Layer: about 0.000013 OKB to create the gate, and about 0.0001 OKB per release (propose, publish, the 3 manifest files). The Free plan is free; Pro (planned) adds a faster watchtower and the verified copy.
An approver loses their key?
The other two can still approve releases (no release needs all three, except admin changes). To replace approvers, your recovery address (kept offline) proposes a new set; it takes effect after 7 days unless two current approvers cancel it, and it works even while the gate is frozen.
Does it slow my site down?
No. Your site is served as before; nothing is added to your pages. Guard checks in the user's browser, and only on sealed domains.
What if my users don't install Guard?
Your team still gets the release approvals and timelock, watchtower alerts, instant freeze, and the public proof and badge. Guard is the extra layer that also blocks the signature for users who run it.
Is my first release slow?
Yes: every first release is tier 10 (2 approvals + 24 h). After that, a code-only release needs 1 approval + 1 h.
