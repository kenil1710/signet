01 / The problem

GitHub was clean.
Users weren't.

Your code passes review on GitHub. Then it's built, hosted, served through a CDN and a domain, and run in the browser. The big front-end attacks happened after GitHub, where nobody was looking.

  1. GitHub your reviewed code clean in every case below
  2. Build + packages npm dependencies Ledger Connect Kit, Dec 2023: a poisoned npm package drained wallets on many dApps
  3. Hosting / CDN files and scripts served Bybit / Safe{Wallet}, Feb 2025: one JavaScript file swapped on the hosting, ~$1.5B BadgerDAO, Dec 2021: a script injected through the CDN, ~$120M
  4. Domain / DNS where the name points Curve Finance and CoW Swap: domain hijacks sent users to a drainer
  5. Browser what your users actually load Signet checks here, against what your team sealed

06 / The rule

A rule nobody
can upgrade.

Pick who approved, what changed and how long it has waited. The release policy answers the way circuit #6 does on X Layer.

Who approved
What changed
under 1 h 1 h+ 24 h+
Switches
PUBLISH 0
UNFREEZE 0

9 inputs, 34 NAND gates, 512 possible cases. UNFREEZE is 1 whenever two approve; the gate only uses it while frozen. The wiring above is drawn for clarity; the real netlist is public on X Layer.

TierWhat changed (computed on-chain)To publish
00Code only1 approval + 1 h, or 3 of 3 with the emergency flag
01A new external origin, or a changed SRI hash of a cross-origin script2 approvals + 1 h
10A new contract or spender. Every team's first release is tier 10.2 approvals + 24 h, or 3 of 3 with the emergency flag
11Admin: approvers, timelocks, domain binding, circuit copy3 of 3 + 24 h, no fast lane

Frozen: nothing publishes. Any one approver can freeze; unfreezing needs 2 of 3. The 1 h and 24 h waits are the defaults; a team can change them (10 min to 5 days) only through a tier-11 change.

Where the decision is made. On every publish and unfreeze, the gate calls circuit #6 on X Layer. It uses a Solidity copy of the same 34 gates (checked equal on all 512 inputs) only if that call fails or returns a malformed answer, or if the circuit's implementation is no longer the one pinned when the gate was made; each fallback emits an on-chain event. Why a circuit: its beacon has no owner, so its logic can't be upgraded, and a gate can only ever point at a copy of the same netlist. The team can change who approves and how long it waits, never the rule.

The 12 attacks, and how to rerun them
  1. DNS / registrar hijack: whole site replaced, drainer on load
  2. One lazy-loaded JS chunk swapped on the CDN
  3. Bundle tampered for one request, then swapped back (as at Bybit)
  4. A script from an unsealed origin injected into the HTML
  5. Code built from data with eval / new Function (no file changed)
  6. A malicious service worker that outlives the hijack
  7. A swap on the sealed router with the attacker as recipient
  8. Permit2 and EIP-2612 permits naming the attacker as spender
  9. A poisoned dependency the approvers publish anyway
  10. Rollback to an older release inside its 6 h grace window
  11. Rollback after the grace window
  12. Signing on a release the approvers revoked

Setup: an anvil fork of X Layer mainnet, fresh projects sealed with the real CLI, headless Chromium and a mock wallet that records every request.
