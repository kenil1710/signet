# Judge review 4 (2026-11-25, independent, public evidence only)

Sources: the public site (raw HTML, no JavaScript), the public GitHub repo `kenil1710/signet` (through `gh api` and raw.githubusercontent.com), the npm registry, the Guard 0.3.4 release asset, and read-only calls to X Layer mainnet (chain 196). I did not read anything in the local working tree.

## 1. Scores

| Criterion | Score | Why |

## 2. Prize odds

- **Competitors.** I found **no public information** on Fusebox, Forgeout, Gavelock or PayProof (web search, and GitHub search for name + tapeout/xlayer: 0 repos). Two other entries in the same field are visible: **Fizzl** (presign-guard for AI agents on X Layer, plus an x402 endpoint directory) and **Vouchgate** (X Layer transaction risk screener over MCP with x402 billing). Both overlap with Signet's "check before you sign" story and ride the x402/AI-agent trend that OKX is pushing.
- **What usually wins** OKX/X Layer programs: the stated criteria are product value, UX, commercialization potential and ecosystem technology use. Winners tend to be consumer-facing apps with a slick demo video and visible users or transactions, or payment and agent rails (x402, USDT0) that grow X Layer activity. Deep security infrastructure with no users tends to land in a "best technical" slot, not 1st.
- **My estimates:** **any prize ≈ 40–50 %** (it is technically the most verifiable entry I can see, and it really uses TapeOut circuits on mainnet). **1st place ≈ 10–15 %** (no video, no outside users, a sideloaded extension with 3 downloads, and no story for X Layer transaction volume or commercial pull).

## 4. Broken, confusing or overclaimed

**Broken**
- `https://signetguard.xyz/api/check?domain=signetguard.xyz` reports **"Releases are not sealed"** (`sealed: null`) for Signet's own sealed site. The same happens for misthos.world. A judge who tries the free risk check on the project's own domain sees the product contradict itself. The same check also flags signetguard.xyz for no HSTS, no frame protection and `script-src 'unsafe-inline'`.
- `https://www.signetguard.xyz/` returns **HTTP 522** (a Cloudflare origin error).
- `https://signetguard.xyz/llms.txt` links resolve against the site and return **404**: `JUDGES.md`, `CLAIMS.md`, `claims.json`, `THREAT_MODEL.md`, `docs/mainnet.md`, `docs/signet-spec.md`, `docs/attack-report.md`, `docs/TRY-IT-LOCALLY.md`, `docs/decisions.md`. Only `docs/CLAIMS.md`, `docs/THREAT_MODEL.md` and `docs/benchmark.md` exist on the site. The file meant for AI judges sends them to dead links.
- `https://signetguard.xyz/prove` is a meta-refresh stub (`./app#/prove`) with a relative `canonical` URL. Without JavaScript, the "proof" is a single sentence.
- OKX explorer links (`web3.okx.com/explorer/x-layer/...`) return 403 to non-browser clients. They are fine in a browser, but crawlers and AI judges can't follow them. The README's Sourcify link is the better one to lead with; I checked that all three contracts are an exact match on Sourcify.

**Stale or contradictory**
- Enforce mode: on-chain `enforced()` = **true** for gate `0xa3d4…4503` (tx `0x00de54492ffa1a2a0574d9d3664e407b0586d8d711bcd95910feabf5b9952dd0`, block 76,840,474). Still saying observe: `CLAIMS.md` ("Claims we do not make … both gates … observe"), `JUDGES.md` L108, `THREAT_MODEL.md` L111, `llms.txt` ("Observe mode"; "Not live: enforce mode on any mainnet gate").
- Release count: llms.txt and THREAT_MODEL stop at "#10 on 2026-11-25", while the chain has `currentRelease()` = **12**. The README hero image caption says "sealed release #9".
- `claims.json` `checkedAt` is **2026-11-21** (block 76,479,734). It is 4 days old and predates releases #7–#12, misthos and enforce.
- Test count: README and JUDGES say "189 Foundry tests". The workflow comment says "190". The CI log says **173 passed, 17 skipped (190 total)**. Every `*.fork.t.sol` test is skipped in CI, including `test_fork_mirrorEqualsRealCircuit6_all512Inputs` and `test_fork_endToEnd_realCircuit_realSiteRegistry`.
- Mock wallet vs Rabby: CLAIMS, THREAT_MODEL, JUDGES and /start say "mock wallet only". `docs/mainnet.md` says "The real-wallet test with Rabby passed".
- README package table: `packages/extension` is "staging; not in the Web Store", yet Guard 0.3.4 is a mainnet build. The README says "No project's files are uploaded yet" in the TapeOut table, while JUDGES says "Release #8's 29 files are stored there in full".
- Watchtower: README says "every 5 minutes on GitHub Actions". The other docs say it is started by a Cloudflare Worker cron. Both are true, but the README alone reads as the 4–12 h GitHub schedule the team itself calls unreliable. The watchtower also only watches **signetguard.xyz**, not misthos.world (`/api/watchtower`).
- `CLAIMS.md` R9 and `docs/benchmark.md` mention "TEE Shield", which is not introduced anywhere a judge would look. This is confusing.
- `docs/mainnet.md` links `internal/launch/07-enforce-plan.md` and `internal/launch/enforce.js`. Neither exists in the public tree (`internal/` returns 404).

**Overclaimed**
- "No single hacked key can change your site" (home, README, JUDGES, llms.txt). A hosting, CDN or DNS credential still changes what visitors without Guard load, which is most visitors. Signet detects the change and refuses Guard users, but it does not prevent it. /start goes further: "Deploy only after `signet wait` succeeds: that is what makes an unapproved build unable to go live". That is only true if the deploy credentials are not stolen, and Signet's own release script deploys before publishing.
- "Release approvals nobody can bypass" and "Changing approvers or waits takes 3 of 3 + 24 h". That holds for the rules, but the code allows **instant 2-of-3 actions with no timelock**: `voteRemoveGuardian()` (used on 2026-11-24, txs `0xf70abd8c…37ce` and `0x251214a3…87be`) and `voteRemoveFile` while revoked. A **single approver** can `revoke` the current release at once, which in enforce mode turns the site red for every Guard user. These are defensible choices, but they aren't "3 of 3 + 24 h".
- "No single key" for Signet's own gate: since #7 every release was published with **approver A alone** plus the CI key. `policyInputs` = 25 or 9 shows only bit a0. All three approvers and the recovery address are the same on the team's two gates, and the repo has one contributor. The 3-of-3 admin guarantee is real in code, but in this deployment it is most likely one person holding several keys.
- "Benchmark: 12 of 12 blocked". The attacks were written by the team, run on a local fork against their own demo dApp, and are not reproduced in CI. Attack #9 ("approvers publish the poisoned package anyway") counts as blocked only because of the default recipient rule, which the report itself admits.
- In Guard circuit #7, `decoded = 0` (unknown calldata, `eth_sign`) and `frozen = 1` produce **WARN, not BLOCK, even in enforce mode** (`docs/guard-truth-table.md`). A page that matches its seal can still get a blind-signing request through with only a warning. "Guard blocks the signature to any contract the team didn't approve" holds for decoded calls, not for every kind of signature.
- The "verified copy" is mentioned in every pitch (home, README, JUDGES, llms.txt), but it is "built and tested; live with Pro". The gateway is not deployed anywhere public.

## 5. What I verified and how

**Site (curl, raw HTML):** `/`, `/start`, `/check`, `/app`, `/prove`, `/privacy`, `/llms.txt`, `/robots.txt`, `/.well-known/signet.json`, `/api/check?domain=…` (signetguard.xyz, misthos.world, www.signetguard.xyz, app.uniswap.org), `/api/watchtower`, and every `href` on those pages (status codes). `/signetguard-0.2.2.tgz` is byte-identical to the npm tarball (sha1 `46256788…8857`). The served `docs/CLAIMS.md` and `docs/THREAT_MODEL.md` are identical to GitHub main.

**GitHub:** `gh repo view`; contributors (1 contributor, 157 commits since 2026-11-18); `gh release list/view guard-v0.3.4` (assets, downloads = 3); `gh release download` plus `shasum -a 256` (matches `f58f19f2…0b0e`); `gh attestation verify signet-guard-0.3.4.zip -R kenil1710/signet` (exit 0); the unzipped `manifest.json` (MV3; host permissions include the Arc RPCs). `gh run list` (test workflow: 30 success, 6 cancelled, no failures in the last 40; watchtower every 5 minutes, green). The latest test run log: Foundry 173 passed and 17 skipped (all fork tests); circuit tests "netlist equals the reference on all 512 input combinations" passed. I read README, JUDGES, CLAIMS, THREAT_MODEL, claims.json, llms.txt, docs/mainnet.md, docs/benchmark.md, docs/attack-report.md, both truth tables, tapeout-interfaces.md, and `packages/contracts/src/ReleaseGate.sol`.

**npm:** `npm view signetguard` (latest 0.2.2, versions include `0.0.0-stage`, maintainer `kency17`, no `dist.attestations`/provenance). `npm pack` into a scratch directory without running it: 4 files, one 1.07 MB `signet.mjs` bundle, no install scripts, no dependencies. The only RPC hosts in the bundle are xlayerrpc.okx.com and xlayer.drpc.org.

**On-chain (cast, read-only; rpc.xlayer.tech):**
- Code present at the registry, factory, implementation, both gates (45-byte clones), processor #101, the container and SiteRegistry.
- Site gate `0xa3d4…4503`: `enforced` = true, `frozen` = false, `currentRelease` = 12, `proposalCount` = 12, `guardian` = 0x0. Approvers `0xB9ef…2416`, `0x3280…6dc`, `0x1C47…c74c`; recovery `0x6940…cD93`.
- Misthos gate `0xDfFf…4a59`: observe, `currentRelease` = 1, the same approvers and recovery.
- `policyInputs` decoded per proposal. Site gate: #3 tier 10 with 3/3; #4, #5, #7, #8 tier 00 with A only; #6 tier 11 with 3/3; #9–#12 tier 00 with A only, after 1 h. Misthos #1: tier 10 with 2 approvals after 24 h.
- Receipts of publish #7–#12 and of `enforce()`: `Published` tier = 0 for all of them, sent by the CI proposer `0x9327…9453`. No `PolicyFallback*` events. `Enforced` from approver A.
- Processor #101: `circuitInfo` = (2,1,0,2) for #5, (9,2,0,34) for #6 and (9,3,0,22) for #7. `ownerOf(5/6/7)` = the site gate. The circuit beacon `0xf70d…991C` has `owner()` = 0x0 and `implementation()` = `0x977f…29B2`. The processor code hash is `0x57aa306f…17d5`, which matches CLAIMS C5.
- **My own 512-row check of both circuits** (my own Python script making `eth_call`s to `eval`, compared with the published markdown truth tables): circuit #6 has 0 mismatches. Circuit #7 maps exactly ALLOW→0x01, WARN→0x02, BLOCK→0x04 on every row.
- JUDGES.md one-liners: `eval(6,0x0b00)` = 0x03 and `eval(6,0xa901)` = 0x00, as documented.
- Sourcify v2: registry, factory and implementation are an `exact_match` (verified 2026-11-24).

**misthos.world:** live on Vercel, an Arc USDC "AI pays your community" app built for a Circle × Arc hackathon (repo kenil1710/misthos, same single contributor). It serves `/.well-known/signet.json` naming gate `0xDfFf…4a59`. It shows no Signet badge, and the watchtower doesn't watch it. **Verdict:** it adds a real server-rendered integration test, which proves the sealing works on a non-trivial 423-file SSR app. But it is **not** a second integrator. It brings Arc host permissions into the X Layer extension, and to a judge it reads as the developer cross-promoting another hackathon entry. Net effect: slightly negative to neutral.
