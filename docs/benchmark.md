# Benchmark: SRI vs a hash-only checker vs Signet

**Against the same 12 attacks on a fork of X Layer, SRI alone blocked 2, a hash-only checker blocked 7, and Signet blocked 12, with 0 false blocks on 16 clean sessions.**

**Read this first:** we wrote these 12 attacks ourselves and ran them on our own local anvil fork of X Layer, not on live sites or a third-party test set. The "hash-only" column is **Signet Guard with its signature checks switched off**, not another product.

Generated by `pnpm benchmark` (`packages/attacks/src/benchmark.ts`) on 2026-11-28. Each defender ran the full
attack suite in its own run, with fresh projects sealed through the real CLI on the staging chain (an anvil fork of
X Layer mainnet), real headless Chromium, and a mock wallet that records every request it receives. An attack is
**blocked** only if the attacker's signature request never reached the wallet.

| Defender | What it is |
|---|---|
| (a) SRI only | No extension. The site puts an `integrity` (SRI) attribute on every `<script>` and stylesheet in its HTML, the best a careful team can do with the browser alone. |
| (b) Hash-only checker | An extension that compares the bytes the page loaded with hashes published on-chain and blocks the page on a mismatch, with **no signing-time check**. This is the approach of TEE Shield and Meta Code Verify. It is modelled here as Signet Guard with its sealed allowlist switched off (`GUARD_MODE=hash-only`), not as those products themselves. |
| (c) Signet | Guard: the page check plus the signing-time allowlist decided by the Guard circuit, enforce mode. |

## Results

| Attack | (a) SRI only | (b) Hash-only checker | (c) Signet |
|---|---|---|---|
| DNS / registrar hijack: whole site replaced, drainer on load | missed | **blocked** | **blocked** |
| one lazy-loaded JS chunk swapped on the CDN/S3 | missed | **blocked** | **blocked** |
| bundle tampered for one request, then swapped back (Bybit) | **blocked** | **blocked** | **blocked** |
| <script> from an unsealed origin injected into the HTML | missed | **blocked** | **blocked** |
| code from data via new Function / eval (no file changed): approve and transfer to the attacker | missed | missed | **blocked** |
| malicious service worker that outlives the hijack | **blocked** | **blocked** | **blocked** |
| swap on the sealed router with the attacker as recipient | missed | missed | **blocked** |
| Permit2 and EIP-2612 permit signatures naming the attacker as spender | missed | missed | **blocked** |
| poisoned dependency adds a drainer address, origin and approve/transferFrom calls; approvers publish it anyway | missed | missed | **blocked** |
| rollback to release 1 inside the 6 h grace window, for a user whose Guard saw release 1, approving a spender release 2 retired | missed | missed | **blocked** |
| rollback to release 1 after the grace window | missed | **blocked** | **blocked** |
| signing on a release the approvers revoked | missed | **blocked** | **blocked** |
| **Blocked** | **2/12** | **7/12** | **12/12** |
| **False blocks on clean sessions** | 0/14 | 0/16 | 0/16 |

## Known misses (not in the 12; Signet doesn't stop these)

The 12 attacks are ones Signet is built to stop. These get through, and are documented as limits rather than counted
(`THREAT_MODEL.md`):

| Attack | Why it gets through |
|---|---|
| A user without Guard (the same DNS hijack) | Nothing checks the page or the signature; the watchtower alerts the team (run in the attack suite: reached the wallet) |
| Code that arrives as data (XSS, a compromised config API) calling a sealed contract with arguments Guard doesn't decode (threat 3b) | The contract is sealed, and Guard doesn't check amounts or unknown arguments; unsealed spenders and recipients are still refused |
| A wallet Guard can't see: Trust Wallet through `window.ethereum` | It talks to its extension over a private message channel and its provider can't be wrapped |
| A cross-origin iframe on a sealed page | The wallet shows the iframe's own origin; Guard covers same-origin iframes only (0.3.7) |
| A look-alike domain (threat 12) | Not sealed, so Guard does nothing there; the user must reach the real domain |
| Observe mode (the default for a new gate, at least 7 days) | Guard reports, never blocks |
| A malicious release that passes approval (one approval + 1 h for code-only changes) | It is the team's sealed release; Signet makes it public and slow, not impossible |

## Rerun it

Needs Node ≥ 22.18, pnpm, [Foundry](https://getfoundry.sh) (`anvil`, `cast`, `forge`), Playwright's Chromium
(`pnpm exec playwright install chromium`), and an X Layer mainnet RPC to fork from in `.env`
(`XLAYER_RPC_URL=https://xlayerrpc.okx.com`). Nothing is sent to mainnet; the fork only reads it.

```bash
pnpm install
pnpm staging:up      # anvil fork of X Layer mainnet + Signet's contracts deployed on it
pnpm benchmark       # the 3 defenders x (12 attacks + clean sessions); rewrites this file
```

About 11 minutes on a laptop. The attacks, the clean sessions and the scoring are in
`packages/attacks/src/suite.ts`; `benchmark.ts` runs it once per defender. `ATTACKS_TRACE=1` prints how long each
attack took; a failed run names the attack it failed in.

**An intermittent failure, found and fixed (2026-11-19).** One rerun stopped after 6 attacks with no message. The
message was lost because the suite exited before macOS flushed the pipe (now written synchronously). The failure
itself: each attack starts a browser with Guard and waits for Guard's first sync of the sealed-domain list; when that
sync failed (an RPC error or the two RPCs disagreeing for a moment), Guard waited for its 5-minute alarm. Saturating
every CPU core reproduced it. This was a real Guard bug (a fresh install on a bad network had no protection for 5
minutes): Guard now retries after 2, 5, 10 and 20 s, then by a one-minute alarm. Reruns after the fix (each on a fresh fork): 5 of 5 passed with the same numbers, and 1 more with half the CPU cores saturated (the conditions of the original failure) also passed.

## Reading it fairly

- **The hash-only column is an ablation of Signet**, not a test of TEE Shield or Meta Code Verify. It shares Guard's page check (cache reads, service-worker check, two RPCs), which may be stronger or weaker than theirs. What it isolates is the value of checking *signatures* against a sealed allowlist, not just *files* against hashes.
- **SRI is given its best case**: every script and stylesheet in the HTML carries an integrity attribute. SRI can't protect the HTML itself (an attacker who serves the HTML writes new integrity values) and doesn't cover chunks loaded with `import()`.
- **Clean sessions**: SRI has no verified-copy sessions (it has no gateway), so it ran 14 instead of 16.
- **Not in this table:** a user without any extension is not protected by (b) or (c) either; that case is in `docs/attack-report.md` as a stated limit. A compromised extension defeats (b) and (c) (`THREAT_MODEL.md`).
